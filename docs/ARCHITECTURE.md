# Архитектура RdpProxy

Документ описывает компоненты и границы ответственности для разработчика.
Для установки используйте [README](../README.md), для формата сообщений —
[протокол](PROTOCOL.md).

## Компоненты и направление данных

Оба адаптера — отдельные процессы Windows x64 с Windows Forms и целевой
платформой `net8.0-windows`. Роль Client/Server обозначает сторону RDP.
Mode независимо выбирает сторону SOCKS5 и сторону исходящего TCP.

| Компонент | Ответственность |
| --- | --- |
| `src/Client` | COM LocalServer, плагин DVC, приём событий RDP-клиента, native-записи через `IWTSVirtualChannel.Write` |
| `src/Server` | Открытие DVC своей WTS-сессии, `ReadFile`/`WriteFile` с persistent OVERLAPPED, повтор открытия |
| `src/Common/LocalProxy.cs`, `SocksServer.cs` | Loopback-слушатель и SOCKS5-аутентификация/CONNECT |
| `src/Common/Session.cs` | Один DVC, handshake, мультиплексирование и планирование кадров |
| `src/Common/ProxyStream.cs` | TCP-сокет одного потока, кредитное окно, FIN/RESET |
| `src/Common/Protocol.cs` | Бинарный формат и сборка кадров |
| `src/Common/Credentials.cs` | Auth-файл, генерация пароля и экспорт сессии |
| `src/Common/TrayHost.cs` | Меню трея, окно статуса и завершение приложения |
| `src/Common/StatusHost.cs`, `Diagnostics.cs`, `TransferMetrics.cs` | Локальный статус, журналы и агрегаты времени |

В ServerProxy слушатель сервера выбирает DVC своей WTS-сессии. OPEN
обрабатывается на клиенте: там выполняются DNS и TCP connect. В ClientProxy
стороны меняются местами. Если у клиента несколько готовых DVC, выбор
отклоняется до OPEN, чтобы не использовать произвольную удалённую сеть.

## COM и жизненный цикл

Регистрация хранится в HKCU текущего пользователя в представлениях x64
и x86. Это позволяет 32-разрядному RDP-контролу активировать отдельный
64-разрядный COM LocalServer. Для новой регистрации RDP-клиент должен
пересоздать свои процессы или контролы.

UI работает в STA-потоке. Клиентский COM LocalServer создаётся, обслуживается
и освобождается в отдельном MTA-потоке. Серверный native I/O работает
в выделенном потоке. Завершение отменяет фоновые операции и дожидается
освобождения каналов, TCP-сокетов и native I/O.

На сторону допускается один адаптер в пользовательской desktop-сессии;
ограничение обеспечивается именованным mutex. Статус передаётся через
named pipe с идентификаторами пользователя, стороны и Windows SessionId.
Слушатель SOCKS5 занимает loopback-порт компьютера, поэтому разные
RDP-сессии одного сервера должны выбирать разные порты.

## Изоляция каналов

Каждый экземпляр COM-плагина имеет OwnerId — локального владельца
RDP-контрола. Каждый DVC имеет отдельные ChannelId и Session. StreamId
уникален внутри DVC; ключ маршрутизации — пара `(ChannelId, StreamId)`.
Одинаковые номера потоков разных каналов не смешиваются.

Отключение или завершение плагина закрывает каналы его OwnerId. Приём
канала согласован с отключением; поздние callback не возвращают закрытый
канал в работу. На клиенте writer начинает работу после HELLO сервера.
Принятый канал без завершённого HELLO закрывается через 15 секунд.

## Транспорт и управление потоком

Клиент делит прикладной кадр на native-записи не более 1200 байт.
Сервер отправляет полный прикладной кадр одной `WriteFile`, максимум
16398 байт с заголовком. Это разные ограничения двух native API.

При чтении на сервере `CHANNEL_PDU_HEADER` разбирается отдельно от
прикладного формата. `NativeRecords` проверяет длину и FIRST/LAST,
собирает запись клиента и только затем передаёт данные `FrameDecoder`.
Парсер кадров не зависит от границ native-записей и callback.

Сервер держит отдельные OVERLAPPED для чтения и записи. Тайм-аут ожидания
не отменяет незавершённое чтение. При остановке native-запросы отменяются
и завершаются до закрытия WTS-канала. Ожидающий writer просыпается по
сигналу исходящей очереди; пока запись выполняется, ожидание ориентировано
на её завершение и чтение.

На канал допускается 64 потока. Каждый имеет окно 256 КиБ на направление
и исходящую очередь до 256 кадров. Входной кольцевой буфер растёт от
16 до 256 КиБ. После записи DATA в TCP-сокет получатель возвращает кредит.
Медленный получатель останавливает чтение TCP своего потока.

Управляющие сообщения имеют отдельную очередь до 4096 кадров. Возвраты
кредита объединяются по потоку; после восьми кредитных кадров планировщик
проверяет DATA/FIN. Обязательные управляющие кадры сохраняют приоритет.
FIN следует за данными своего направления; второе направление продолжает
работать. RESET закрывает весь поток.

## Отказы и границы доверия

Ошибка локального TCP-сокета закрывает его поток. Нарушение протокола
или потеря DVC закрывает все потоки канала. Повтора кадров и восстановления
передачи после нового DVC нет. Сервер повторяет открытие через 3 секунды;
отсутствие входящих кадров в течение 15 секунд завершает канал.

SOCKS5 проверяет имя и пароль локально до OPEN. HELLO проверяет роли,
режим и версию, но не является отдельной аутентификацией узлов. Доверие
к противоположной стороне опирается на установленное RDP-соединение.
Дополнительное шифрование поверх RDP не реализовано.

Разрешены все TCP-назначения, доступные стороне исходящих подключений.
Приложение не меняет маршруты и DNS системы. Секреты хранятся в локальных
JSON-файлах с ACL пользователя; процессы этого пользователя и администратор
ОС имеют доверенный доступ. Статус и журналы не публикуют пароли или payload.

Метка сборки берётся из `AssemblyInformationalVersion`. Закреплённый SDK
10.0.404 обеспечивает выбор инструмента сборки, но не переводит runtime
приложений с .NET 8 на .NET 10. Миграция целевой платформы и проверка
реального GUI/RDP-сценария нужны отдельно до стабильного выпуска.
